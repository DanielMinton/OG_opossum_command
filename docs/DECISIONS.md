# Decisions — OG Opossum Command Central

Pre-approved by the operator (22 Oct 2026). Format: decision · why · revisit when.

- **ADR-000 · Name.** Product "OG Opossum Command Central"; code name `OG_opossum_command` (exe `OG_opossum_command.exe`, data `%LOCALAPPDATA%\OG_opossum_command`). Supersedes "OPOSSUM CONTROL" in the spec. · Operator's choice. · Never.
- **ADR-004 · One tray process.** Hiding the window keeps workflows running; quitting stops them. · Simplest lifecycle for daily use. · Workflows must survive a full app exit.
- **ADR-005 · WPF on .NET 10 LTS.** · No MSIX packaging, mature tray support, per-user deployment. · A WPF limitation blocks a needed feature.
- **ADR-008 · SQLite for runs and history; JSON files for workflow definitions.** · Workflows stay hand-editable and diffable without an editor. · A visual editor is built.
- **ADR-011 · Calendar via Power Automate → OneDrive JSON file.** · Works with New Outlook; no app registration or admin consent. · IT approves a Graph app registration.
- **ADR-012 · Strict work/personal separation.** No data, tokens, or files cross the YMCA and Ohana tenants; enforced in the engine, not just the UI. · Never.
- **ADR-013 · AI deferred.** Not part of this build. · Spec Phase 5 is started deliberately.
- **ADR-014 · Feasibility spike shape.** One console-type (`OutputType=Exe`) WPF project under `spikes/feasibility/Spike`, WPF `Application` and `TaskbarIcon` created in code (no App.xaml), SQLite opened with `Pooling=False` so the file can be deleted, 55 s watchdog in both modes. · `--check` must print to the console under `dotnet run` and exit on its own within 60 s; a second entry point from App.xaml would break the single-project rule. · The spike is deleted or the real Desktop project supersedes it.
- **ADR-015 · Repo-level `nuget.config` with nuget.org as the only source.** · The user-level `%APPDATA%\NuGet\nuget.config` on this PC has an empty `<packageSources>` list, so every restore failed with NU1100; the fix lives in the repo because the build never writes outside the project root (rule 5), and it makes restores reproducible on any machine. nuget.org is reachable anonymously; no sign-in is involved. · The user adds nuget.org to their user-level config, or the project moves to a private feed.
- **ADR-016 · Desktop entry point.** `OutputType=WinExe` (no console window for a tray app) with a hand-written `Program.Main` selected by `<StartupObject>`; `App.xaml` stays the `ApplicationDefinition` (no `StartupUri`) so later `--smoke-ui` runs with real resources. `--smoke-test` is handled before `App` is constructed; it writes to stdout, which a windowed exe only delivers when the caller redirects it, so the **exit code is the contract** and the build script checks only that. · Diagnostic modes must never show a window or run startup work; the gate captures output anyway. · A mode needs interactive console output (then split a console launcher).
- **ADR-017 · Tests on xUnit 2.9.3 + xunit.runner.visualstudio 3.1.4 + Microsoft.NET.Test.Sdk 17.14.1, versions pinned.** `Microsoft.NET.Test.Sdk` is the VSTest host the gate's `dotnet test --blame-hang-timeout` needs; it counts as "the xUnit runner" under rule 8. The template's `coverlet.collector` was removed (not on the allowed list, not needed). · The gate's exact command must work. · The gate moves to Microsoft.Testing.Platform.
- **ADR-018 · CA1707 and the underscore code name.** `AnalysisLevel=latest-recommended` flags `OG_opossum_command` as an assembly name and as a namespace. A namespace-scoped `SuppressMessage` does not match (Roslyn attributes the diagnostic to the innermost declared namespace) and an unscoped one disables the rule everywhere (verified with a probe). Instead, `CodeNameSuppression.cs` at the repo root is the first compile item of every project (via `Directory.Build.props`), carries the only `#pragma warning disable CA1707`, and declares an empty `namespace OG_opossum_command` so both diagnostics land inside the pragma. Every other identifier is still checked; a planted `Bad_Name()` method fails the build. · Rule 0 asks for the narrowest suppression. If compile order ever changes, the diagnostics reappear and the build fails loudly rather than widening. · Roslyn offers a precise way to suppress assembly-level diagnostics.
- **ADR-019 · CA1707 off under `tests/` only.** `tests/.editorconfig` sets `dotnet_diagnostic.CA1707.severity = none`, because test method names use underscores for readability. `src/` is unaffected. · Standard xUnit naming. · Never.
- **ADR-020 · AppPaths contract.** One sealed `AppPaths : IAppPaths` in Core resolves everything from one root: `OGOC_DATA_DIR` if set and **absolute**, else `%LOCALAPPDATA%\OG_opossum_command`. Blank values count as unset; relative values throw (never the current directory). Resolving is pure (creates nothing); `Resolve(getEnv, localAppData)` takes injected inputs so tests never mutate the process environment, and `FromEnvironment()` is the only production entry. Child paths (revised in Phase 3): `data.db`, `profiles\`, `profiles\<Work|Personal>\workflows\`, `logs\`; there is no shared `workflows\` folder because every workflow belongs to exactly one profile (ADR-012). · Rule 6, plus flaky parallel tests if they set env vars. · A path is needed outside the data root (it must be a new property here, not computed elsewhere).
- **ADR-021 · Root `Directory.Build.props` also governs `spikes/`.** The spike is not in the solution and is throwaway (ADR-014); it inherits the stricter analyzers but is never built by the gate. · One props file, no exceptions to maintain. · The spike is deleted.

## Phase 3 (core loop)

- **ADR-022 · Workflow schema v1 is strict and small.** Unknown properties, wrong types, non-slug ids, unknown actions, bad `dependsOn` (unknown, self, cycle), and `requiresApproval: true` are all errors; comments and trailing commas are tolerated; `trigger.type` is `manual` only; `onDuplicate` is `focus-existing` only; `onFailure` is `stop` | `continue`; there is **no `retry`**. Full contract in `docs/WORKFLOW-SCHEMA.md`. · Hand-edited files fail loudly on typos instead of silently doing something else; the reserved flag cannot be abused before the approval flow exists (ADR-013); retry of a process launch is unsafe (spec §06) and the other v1 actions finish instantly. · Schedules (Phase 2 of the spec), retry, or AI approval are built — each needs a schema bump, and old files must still load.
- **ADR-023 · Actions validate their own typed inputs at load time.** `IWorkflowAction.ParseInputs(JsonObjectReader)` turns the step's `inputs` object into a typed record (`UrlOpenInputs`, `FolderOpenInputs`, `ProcessLaunchInputs`) or records readable errors; the engine never sees a dictionary. `windows.process.launch` takes a full `.exe` path plus an argument **array** (passed to `ProcessStartInfo.ArgumentList`, no shell); `windows.url.open` accepts absolute http/https only, checked again at run time; `%VAR%` expansion happens at run time so files are portable. · Spec §07 (“avoid implicit string interpolation into shell commands”, “strongly validated DTOs at security boundaries”). · A scripting action is wanted (it gets its own action id and its own validation, not a relaxation here).
- **ADR-024 · In-process engine, one cancellation source per run, explicit process-tree kill.** `WorkflowEngine` runs on the thread pool with a `SemaphoreSlim` of `MaxConcurrentWorkflows` (default 2) run slots and `maxParallelSteps` step slots per run; each step gets a linked token with its timeout; on cancellation or timeout the process action calls `KillTree()` itself because a cancelled token is not process termination (spec §06). Every transition is saved before `ExecutionChanged` fires with an immutable snapshot (on worker threads; the UI marshals). `Interrupted` is only ever set by startup reconciliation; `NeedsAttention` exists in the enum but nothing sets it yet. · Simplest design that satisfies §06 and rule 8; snapshots make the UI and tests trivially thread-safe. · Resume/recovery review (spec Phase 2) is built, or a second host process is ever introduced (ADR-004).
- **ADR-025 · Profiles are fixed (Work, Personal); allowlist from an optional `profile.json`; default is every built-in action.** `profiles\<P>\profile.json` with `{"allowedActions":[...]}` narrows a profile; without it, the profile may run all registered actions. A broken policy file is reported in `ProfileCatalog.Errors` and on the smoke output, and the profile falls back to the default. The loader rejects disallowed actions per file and the engine refuses them again at `Start` (defence in depth, ADR-012). · In v1 every action is local and benign, so a typo in a policy file should not lock the user out of their own tiles; the double check means a definition can never bypass the allowlist. · **Revisit (fail closed) the moment a network, M365, export, or AI action exists** — then an unreadable policy must deny those actions, not allow them. **Revised in Phase 5 by ADR-040** (the first M365 action exists: defaults and the broken-file fallback now exclude `m365.*`).
- **ADR-026 · Smoke modes never touch the real data root and run before the single-instance check.** `--smoke-test` and `--smoke-ui` use `OGOC_DATA_DIR` when set (the build script's scratch folder) and otherwise a fresh `%TEMP%\OG_opossum_command-smoke-<guid>` folder deleted on exit; both carry a 25 s watchdog that exits 1; both use `RecordingLaunchers`, so no browser, folder, or program opens (rule 7). `--smoke-ui` constructs the real `App` with `App.xaml` resources, shows `MainWindow` at (-32000,-32000) with `ShowActivated=false`, waits for `Loaded` and the dashboard's first bind, creates and disposes the tray icon, then shuts down. · Rules 5–7 and the operator's smoke contract. · A smoke mode needs more than one profile's data (then give it its own fixture folder).
- **ADR-027 · Tray icon uses `System.Drawing.SystemIcons.Application`.** It comes from the WindowsDesktop shared framework that WPF already references, so no new package (rule 8); the spike proved the exact calls (`ToolTipText`, `Icon`, `ForceCreate`, `Dispose`). The context menu (Open / Switch profile / Quit) is built in code so the smoke runner can create and dispose it deterministically. · No icon asset exists yet and the generic icon is unmistakable in the tray. · An `.ico` is designed (then set `IconSource` from an embedded resource and delete this line).
- **ADR-028 · Single instance via session-local kernel objects.** `Program.Main` (after the smoke switches) takes `Local\OG_opossum_command.instance` as a named mutex; a second instance signals the auto-reset event `Local\OG_opossum_command.show-dashboard` and exits 0, and the first instance's background listener thread shows the dashboard. Both objects are session-scoped (`Local\`), need no elevation, and touch neither the registry nor the network (rules 2–4). · Spec §05 B (“one authoritative instance per Windows user”); pressing the shortcut twice should bring the window forward, not open a second app. · IPC beyond “show yourself” is needed (then a named pipe with an allowlisted command set, still local).
- **ADR-029 · Dashboard shows exactly six tiles; History is a separate view; closing hides to tray.** The first six workflows of the active profile (sorted by file name) fill the tiles and the rest are disabled “Empty slot” placeholders, so positions never shift (spec §14); files that fail validation are listed on the dashboard with their errors; the Active execution panel shows live steps and a prominent Cancel; Recent runs shows the last 8; the History view lists the last 100 runs with per-step detail and the redacted event log. Colours come from `SystemColors` dynamic resources so Windows high-contrast themes apply; every control has an automation name and the shared focus visual. The active profile is remembered in the `settings` table. · Spec §14 mock-up and the acceptance test “Accessibility”. · Favourites/ordering beyond file name, or more than six workflows per profile become common.
- **ADR-030 · Tests may start `cmd.exe` and `ping` as throwaway processes; such tests run in one xUnit collection.** `WorkflowEngineTests` and `WindowsProcessLauncherTests` share the `"real processes"` collection so their ping-process bookkeeping (snapshot PIDs, wait for the new one, assert it is gone after `KillTree`) is never interleaved; everything else uses `RecordingLaunchers`/`FakeProcess`. · Rule 7 permits exactly these throwaways; the first parallel run was flaky because two classes counted the same `PING.EXE` instances. · A dedicated test helper exe replaces `ping` as the long-running child.

## Phase 4 (reliability)

- **ADR-031 · `windows.script.run` runs trusted scripts only, from the profile's own `scripts` folder.** Inputs are an explicit `interpreter` (`powershell` → `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -File <script>`, or `cmd` → `cmd.exe /d /c <script>`), a bare `script` file name (no separators, no `..`, extension must match the interpreter, resolved path re-checked at run time to be inside `profiles\<P>\scripts`), and an `arguments` array. It reuses `IProcessLauncher` (8 KB per-stream capture, redaction, process-tree kill), so tests and smoke modes stay fake. A PowerShell refusal is detected from the output ("running scripts is disabled", `PSSecurityException`, `UnauthorizedAccess`, …) and reported as `execution-policy-blocked` with the options spelled out; the app **never** passes `-ExecutionPolicy` (rule 2). Tests run a real `.cmd` only; PowerShell behaviour is tested with fakes because policy on this PC may block `.ps1` and the app must not try. · Spec §07/§09 ("treat shell and PowerShell as explicit trusted-action categories"). · A third interpreter is wanted (add a fixed path here; never a free-form path).
- **ADR-032 · Workflow schema v2 is additive; v1 files keep loading.** `CurrentSchemaVersion` is 2, `OldestSupportedSchemaVersion` is 1. New in v2: `trigger.type: "schedule"`, per-step `locks`, top-level `aliases`. A file that says `schemaVersion: 1` and uses any of them is rejected with "needs schemaVersion 2", so an old file never silently gains behaviour. `docs/WORKFLOW-SCHEMA.md` is the contract. · ADR-022 asked for a bump with backwards compatibility. · v3.
- **ADR-033 · Resource locks are engine-wide, taken in sorted order, released in `finally`.** A step may declare `locks: ["window:<name>", "file:<full path>", "custom:<name>"]`; keys are normalised at load time (`file:` → absolute, upper-cased, `%VAR%` expanded; others verbatim with a lower-case kind). `ResourceLocks` holds one `SemaphoreSlim(1,1)` per key for the whole engine, so the same key serialises steps across different runs and workflows even with `maxParallelSteps > 1`. The wait observes the step's own token, so Cancel while waiting takes nothing; a step waiting for a lock stays `Running` with "Waiting for …" and occupies one of the run's parallel slots (accepted; the alternative would reorder steps). · Spec §06 concurrency policy. · Lock contention becomes visible in daily use (then add a dedicated Waiting state).
- **ADR-034 · Scheduler: definition in the file, state in SQLite, `last_fired_for` written before any run starts.** `trigger.type: "schedule"` needs `at` (HH:mm list), an explicit `timeZone` (Windows or IANA ID, validated at load), optional `days`, `missedRuns` (`skip` default | `run-once` | `catch-up-limited` + `catchUpLimit` 1–10), and `expiresAfterMinutes` (default 5). `OccurrenceCalculator` is pure: a time inside a spring-forward gap runs at the first minute that exists; a time inside a fall-back fold runs once, at its first (daylight) pass; the machine's zone is never consulted. `Scheduler.Tick(now)` computes occurrences since `last_fired_for` (capped at 7 days back), splits them into on-time (within the expiry window) and missed (policy), persists `last_fired_for = latest` **before** starting anything (a crash loses at most one run, never repeats one), then dispatches per trigger: on-time occurrences start immediately and are **suppressed** if the workflow is still active (focus-existing); catch-up runs are awaited one after another so the limit means what it says. `Reconcile` registers new or changed schedules from *now* (nothing before they existed counts as missed), keeps state for unchanged ones, and deletes rows whose workflow is gone. A background loop ticks at the next due time, at most every 30 s, using `TimeProvider` so tests inject a clock and call `Tick` directly. While paused (`scheduler.paused` setting) due occurrences are recorded as skipped, so unpausing never fires stale runs. Scheduler decisions without a run (skipped, suppressed, paused) surface as `SchedulerEvent`s and in `triggers.last_outcome`, not as execution events (those need an execution id). · Spec §08 and the acceptance test "Scheduler". · Event or calendar triggers (new `type`, same table).
- **ADR-035 · Crash recovery: classify, auto-resume only what is provably safe, otherwise Needs attention with Resume / Dismiss.** *(Revised by ADR-046: runs found Cancelling end Cancelled; failed or cancelled non-idempotent steps also block auto-resume.)* `MarkInterrupted` now returns the IDs it touched and sets `recovery = pending`; after workflows load, `RecoveryReviewer` classifies each: workflow file missing → Needs attention; `executions.workflow_hash` (new) differs from the current file → Needs attention; any step that was *running* at the crash whose action is `NonIdempotent` → Needs attention naming the step; otherwise a new run starts automatically (`trigger_source = recovery`, `resumed_from` = old id) with the already-Completed steps marked Completed and not repeated. The original run ends `Interrupted` with `recovery` = `auto-resumed` | `resumed` | `dismissed`, or `NeedsAttention` with the explanation in `error`. Resume uses the *current* file. The engine tolerates the journal closing underneath it (a crash or shutdown) without unobserved exceptions. · Spec §13 recovery algorithm; §17 Phase 2 exit criterion "no silent duplicate side effects", proven by tests that close the journal under a running engine. · Adapters gain reconciliation (e.g. "is that process still running?"), which could turn some Needs attention cases into safe resumes.
- **ADR-036 · Single-instance lock lives in Core; smoke modes are exempt; Core declares `SupportedOSPlatform("windows")`.** `SingleInstanceLock.Acquire(name)` tests ownership with `WaitOne(0)` on `Local\<name>.instance` (not `createdNew`, which a lingering handle can fool), owns the `Local\<name>.show-dashboard` auto-reset event, and raises `ShowRequested` on a listener thread; `SignalExisting` is what the second launch calls. Names are parameterised so tests use unique ones; a Windows mutex is re-entrant per thread, so the in-process "second instance" tests acquire on another thread. `Program.Main` runs the smoke switches *before* taking the lock, and a test proves it: it holds the production lock and starts the real exe with `--smoke-test` (path baked into the test assembly as `AssemblyMetadata` by the csproj, built first via a `ReferenceOutputAssembly=false` project reference) with `OGOC_DATA_DIR` set to a throwaway folder in the child's environment. Named kernel objects are Windows-only (CA1416), so Core and the tests carry an assembly-level `SupportedOSPlatform("windows")` rather than changing the TFM. · Spec §05 B; the brief's test requirement; rule 11 with `-warnaserror`. · Core must ever run off Windows (it will not).
- **ADR-037 · Notifications go through one injectable sink; quiet mode suppresses everything below Error.** `NotificationService` (Core) turns engine results and scheduler decisions into `Notification(Level, Title, Message)`; Completed = Info, Cancelled/skipped/suppressed = Warning, Failed/Needs attention/refused = Error. With `ui.quietMode = true` only Error gets through (a failed run or one that needs the operator is never silent). The Desktop sink shows tray balloons via `TaskbarIcon.ShowNotification` on the dispatcher; `--smoke-ui` and tests use `RecordingNotificationSink`, so the build never pops a balloon (rule 7). · Spec §14 "quiet mode and notification severity thresholds". · Windows toast notifications (would need an AppUserModelID; a per-user shortcut is acceptable under rule 2, but not needed yet).
- **ADR-038 · Global hotkey via `RegisterHotKey` on the hidden main window; failure is reported, never thrown; the palette is a separate topmost window.** Default `Ctrl+Alt+Space`, stored as text in `ui.hotkey`, parsed by `HotkeyGesture` (at least one modifier plus one key). `GlobalHotkey` registers on the main window's HWND (`EnsureHandle`, so it works while hidden) and reports `ERROR_HOTKEY_ALREADY_REGISTERED` as "in use by another app; change it in Settings" in the host status line. Not registered in `--smoke-ui` (a build must not grab a system-wide key). P/Invoke uses `DllImport` with `DefaultDllImportSearchPaths(System32)` because `LibraryImport` would need `AllowUnsafeBlocks` project-wide. The palette searches both profiles (`CoreHost.Search`: alias/name equal > starts-with > id starts-with > contains) and labels each row with its profile; Enter runs under that profile, so ADR-012 is unaffected. `--smoke-ui` constructs the Settings view and the palette off-screen so XAML errors fail the gate. · Spec §08 trigger family 1 and §14 "global command palette with human-readable aliases". · A low-level keyboard hook is needed (it is not: hotkeys are enough and far less invasive).

## Phase 5 (calendar without app registration)

- **ADR-039 · Calendar = one read-only local JSON file per profile, written by the user's own flow; strict schema, tolerant reader.** `m365.calendar.readFile` reads the profile's `CalendarFilePath` (from `profile.json` `calendarFile`, else `AppPaths.GetDefaultCalendarFile`: Work → `%OneDriveCommercial%\OG_opossum_command\calendar.json`, Personal → none). The path never comes from a workflow file. `CalendarFileParser` is strict (exact keys, `schemaVersion` 1, ISO 8601 timestamps **with an offset**, bare dates only for all-day events, https-only links, at most 500 events) because the Outlook connector exposes offset-less start/end fields that would silently shift every event. `CalendarService` is tolerant: missing, empty, locked, or not-JSON-yet (mid-sync) files are retried once after 750 ms and then reported as `Unavailable`, and the step **completes**. Only well-formed JSON in the wrong shape (`calendar-invalid`) or a cross-context path (`calendar-refused`, ADR-040) fails the step. It never throws for a bad file. Staleness is judged from `generatedAt` (default 60 min, step input `maxAgeMinutes`), never from the file's mtime. Online-only OneDrive placeholders (offline/recall attributes) are not opened, because opening one triggers a download. The calendar reader never creates or writes anything under OneDrive *(revised in Phase 8 by ADR-050: the exports write `status.json` and `outbox\*.json` into the same app folder)*. Event content stays in memory (`GetLatest`); history stores the status line and counts only. `dashboard.schedule.show` goes through a new `IDashboardPresenter` on `LauncherSet` (the App on the dispatcher; a recorder in tests and smoke runs) and never reads the file itself. It switches the window to the run's profile (and remembers that choice), so a scheduled Work run ending in this step brings up Work even if Personal was showing, which is deliberate: it shows *that run's* schedule. The Today panel reads on profile load and on **Refresh**, with no timer. `AppPaths` gained the OneDrive roots from the same injected environment lookup; `ForRoot` resolves none, and the smoke modes now use `ForRoot(OGOC_DATA_DIR)` instead of `FromEnvironment`, so a build-time smoke run never looks inside the user's real OneDrive (rule 5). The flow itself is the user's job (`docs/POWER_AUTOMATE_FLOW.md`, standard connectors only). · ADR-011 (no app registration; New Outlook has no COM), rules 3–5, and the brief's "never crash". · IT approves a Graph app registration (then a Graph reader replaces the file behind the same `CalendarService`), or the flow needs fields beyond the seven in schema 1 (bump `schemaVersion`; keep reading 1).
- **ADR-040 · `m365.*` actions are Work-only by default and fail closed; a path guard backs up the allowlist.** With no `profile.json`, Work may run every built-in action and Personal every action except the `m365.*` family. A broken policy file now falls back to *every built-in action minus `m365.*`* for either profile, revising ADR-025: local tiles keep working and M365 data is denied. Even when a Personal policy explicitly allows `m365.calendar.readFile`, `CalendarService` refuses any path inside `%OneDriveCommercial%`, and Work any path inside `%OneDriveConsumer%` (after `GetFullPath`, so `..` doesn't help). That makes three independent layers: the loader rejects the file, the engine refuses at `Start`, and the service refuses the path. The guard lives in the service, not only the action, because the dashboard reads through it too. · ADR-012 ("enforced in the engine, not just the UI") and ADR-025's own revisit trigger. · A personal calendar feed is wanted (then a Personal `calendarFile` outside the work OneDrive plus an explicit allowlist entry; the guard already permits that).

## Phase 6 (hardening)

- **ADR-041 · Four adversarial reviews, each verified, fixes on separate worktrees.** Reviewers covered security, stress correctness, accessibility, and simplicity. Each finding then went to a second agent told to refute it. Only the confirmed findings were fixed: 7 of 8 security, 16 of 20 correctness, all 12 accessibility, 12 of 15 simplicity. The refuted ones are C16, C17, C19, C20 (timeout labelling, dispatcher ordering, expiry of resumed scheduled runs, clock-jump spin), SEC-5 (OneDrive alias spellings; the guard is for accidents, not the user), and S11, S14, S15 (`IHistoryStore` seam, the spike, reserved schema fields). · Unverified findings would add risk without fixing anything. · Before the first organisational release, repeat the review.
- **ADR-042 · `cmd` scripts get no shell metacharacters; cmd starts in the scripts folder.** For `interpreter: "cmd"` the loader refuses any argument containing `& | < > ^ % ! " ( )` or a line break, and refuses script names with spaces. It checks the arguments again after `%VAR%` expansion, refuses a UNC scripts folder, and starts `cmd.exe /d /c .\<script>` with the scripts folder as working directory, so the folder path never appears on the line cmd re-parses. That line also never starts with a quote, so cmd's quote stripping can't mangle it. The launcher still takes only an argument array (ADR-023). · cmd re-parses everything after `/c`, so an argument array is only an array when no element is special to cmd. Raw command-line support was rejected so that "no shell strings" stays true. · Someone needs `%VAR%` or metacharacter arguments for cmd (the answer today: use the `powershell` interpreter).
- **ADR-043 · `windows.process.launch` refuses shells and script hosts.** The refused programs are `cmd`, `powershell`, `powershell_ise`, `pwsh`, `wscript`, `cscript`, `mshta`, `rundll32`, `regsvr32`, `wsl`, `bash`, `conhost` and `forfiles`. They are matched by file name, ignoring case, after `GetFullPath`, at load and again at run time (`interpreter-refused`). "Allowed executable" (spec §18 Launch) therefore means a full `.exe` path that is not one of these, inside a profile whose allowlist permits the action. · Otherwise `powershell -ExecutionPolicy Bypass -Command …` or `cmd /c …` skips every ADR-031 rule and any allowlist that leaves out `windows.script.run`. · A legitimate tool ships under one of these names, or name matching proves too weak (8.3 names, renamed copies; the author is the local user).
- **ADR-044 · Strict input: duplicate JSON keys are errors; NUL is checked before `%VAR%` expansion.** `AllowDuplicateProperties = false` applies to workflow files, `profile.json`, and the calendar file. A NUL in a path, a lock, or `calendarFile` is a readable load error, and the calendar service returns Unavailable for it. · `JsonDocument` lets the last duplicate win silently, and `ExpandEnvironmentVariables` cuts a string at a NUL, so a folder path could quietly open its parent. · A tool we read legitimately writes duplicate keys.
- **ADR-045 · Redaction is central, broader, and bounded twice.** `SqliteHistoryStore` scrubs every run error, step message, step output, and recovery explanation it stores. The engine also scrubs step messages and run errors before publishing them (500 characters), so the dashboard and tray never show raw text. The store's own cap sits above the engine's, so nothing is cut twice. New patterns: underscore-prefixed keys (`DB_PASSWORD=`, `GITHUB_TOKEN=`), `Authorization: Basic|Digest|NTLM|Negotiate`, quoted values with spaces, `--token value` style flags, URL user info, and prefixed tokens (`AKIA…`, `ghp_…`, `github_pat_…`, `glpat-…`, `xox?-…`, `sk-…`). The calendar parser no longer echoes a rejected link. · Spec §13 and §18 Output require it, and any caller that forgets to scrub would otherwise leak. · A new secret shape turns up in real output (add a pattern and a test).
- **ADR-046 · Every run transition is saved before it is announced. Recovery reads its work from the database, and operator cancels are final.** Each run has a save gate (snapshot and write together). The Queued, Running, Cancelling, step, and terminal states are all persisted before `ExecutionChanged`. A resumed run records its already-completed steps when it is queued. Recovery reviews every row with `recovery = 'pending'`, not just this boot's list, and each run is reviewed in its own try/catch. Auto-resume is blocked by any non-idempotent step that started, whether it ended Interrupted, Failed, or Cancelled. A run found **Cancelling** at startup ends **Cancelled** and is never resumed. This revises ADR-035, where Cancelling became Interrupted. The engine refuses `Start` once shutdown begins, and Quit stops the scheduler first. After a process exits, the output drain waits at most 2 s, so a grandchild that holds an inherited pipe can't hang a step. The scheduler loop survives store errors and throwing subscribers (it backs off 30 s and records `scheduler.lastError`). · Spec §17: "no silent duplicate side effects during simulated interruption". The operator already chose to stop a cancelled run. · Saves become a bottleneck (switch to a version column), or detached grandchildren need Job-object containment.
- **ADR-047 · Accessibility: live regions that announce, scalable font resources, a dashboard that scrolls.** `Accessibility/LiveRegion.Announce` makes a TextBlock a polite live region and raises `LiveRegionChanged` whenever its text changes, because WPF never raises it on its own. It covers the status line, Today status, the active run headline, host status, the hotkey status, History detail, and palette messages. `Accessibility/FontScale` rewrites the `Ogoc*Size` font resources from `SystemFonts.MessageFontSize` (relative to its default 12 DIP, clamped to 100–225%) at startup and on preference changes; every view uses them through `DynamicResource`. It is **unverified** whether the Windows Text size slider (which writes `TextScaleFactor`) changes that font in WPF. Manual check M5.4 decides; if the slider has no effect, `FontScale` should read `TextScaleFactor` instead. The dashboard sits in a `ScrollViewer`, and Active execution with **Cancel** comes right under the tiles, so Cancel is never clipped. List items expose `AutomationName` through `ToString()`, because WPF item peers read `ToString`. Step rows read "name, status". Resume and Dismiss name their workflow. Access keys are unique per window (Pro**f**ile, Hot**k**ey, Pa**u**se; per-row Resume and Dismiss have none). List rows get the thick focus ring. Placeholder tiles show their hint even while disabled. The palette scrolls to the selected row and announces it. The tray icon answers Enter and Space. · Spec §14 and the §18 Accessibility row. These need no package, and colours were already `SystemColors` only. · A Narrator or high-contrast check on this PC (docs/ACCEPTANCE.md, MANUAL rows) finds a gap.
- **ADR-048 · A metadata test guards "no network, no listeners".** `NoNetworkSurfaceTests` reads the compiled Core and Desktop assemblies with `System.Reflection.Metadata`; nothing is loaded or run. It fails if either references `System.Net.Http`, `Sockets`, `HttpListener`, `WebSockets`, `Requests`, `NameResolution`, or `System.IO.Pipes`, or one of their client or listener types. · Build rule 4 and spec §18 Offline become a test instead of a promise. · An approved network adapter is added (spec Phase 3); it would live in its own assembly with its own policy.
- **ADR-049 · Dead code removed.** Removed: `StepDefinition.RawInputs`, `ActionRegistry.Actions`, `CalendarReadResult.ReadAt` and `FilePath`, `SchedulerEvent.TriggerId` and `OccurredAt`, `SingleInstanceLock.Name`, `NoOpDashboardPresenter` (`LauncherSet.Dashboard` is now required), `ShellViewModel.OpenCommand`, `IsWorkActive` and `IsPersonalActive`, `DashboardViewModel.ProfileName`, `GlobalHotkey.Gesture`, and the duplicate `BoolToVis` converters (now one in App.xaml). `CalendarReadFileAction` uses `CalendarReadResult.IsFailure` instead of repeating its rule. · Rule 8: simplest design that meets the spec. · Never.

## Phase 8-9 (exports and alerts)

- **ADR-050 · Exports live in one OneDrive app folder per profile; Work on by default, Personal off; policy fails closed; `status.json` is small and scrubbed.** *Folder:* `AppPaths.GetDefaultExportsFolder` (Work → `%OneDriveCommercial%\OG_opossum_command`, the folder that already holds `calendar.json`, which `GetDefaultCalendarFile` now derives from it; Personal → none). It is a pure path computation, so ADR-020's "new property here" rule holds. *Policy:* `profile.json` gains an optional `exports` object `{ "folder", "status", "alerts", "carryovers" }`, parsed strictly like the rest of the file (unknown keys and duplicates are errors). With no `exports` object, Work has all three on when `%OneDriveCommercial%` is set and Personal has all off; a switch left out defaults to on for Work and off for Personal. Personal can only be enabled with its own `folder`. `%VAR%` references are allowed, UNC and device paths are refused (writing there would be network I/O), and a folder inside the other context's OneDrive is a policy error **in either direction** (`OneDriveBoundary`, the guard `CalendarService` now shares). That error makes the whole `profile.json` broken, so the allowlist fails closed (ADR-040) and exports are off. A broken or unreadable `profile.json` always turns exports off for that profile, and a Personal folder equal to Work's turns Personal off. *Folder creation:* only the last level (`OG_opossum_command`) is created, and only when its parent exists; a OneDrive root is never created. A missing folder is a Skipped/FolderMissing state, logged once to `logs\exports.log` and shown in Settings. *`status.json` (schema 1):* `StatusExporter` writes it on the first loop pass, every 15 min (driven by `TimeProvider`; `Tick` is testable like `Scheduler.Tick`), soon after any run of the profile ends Completed, Failed or Cancelled or becomes Needs attention (debounced to one write per 30 s), and once on clean exit (`CoreHost.Dispose` after a successful `Open`). The write is atomic (temp file in the same folder, then `File.Move` overwrite). Contents: `needsAttention`, `failed` (at most 20, newest first, with the failed step's message), `failedSince` = **generatedAt minus 24 h** (chosen over "yesterday 16:30" because it needs no local business-hours rule), `completedToday` (local day, counted from the last 1000 runs, so `IHistoryStore` is unchanged for it; ADR-054 gave `GetExecutionsByStatus` a profile filter for `needsAttention`), `runningNow` (includes Queued and Cancelling), and `scheduledToday` (remaining occurrences to local midnight, enabled triggers only, empty while schedules are paused). `profile` is the display name and every timestamp is local with its offset. Every free-text field goes through `OutputRedactor`, then paths become `[path]` and URLs `[link]`, and the text is collapsed to one line and cut to 200 characters. Step outputs and arguments are never written. Only that profile's runs appear. · The Morning Briefing flow needs a summary it can read without the app making network calls (rules 3–4), and ADR-012/040 require the same separation for writes as for reads. · A second consumer needs more fields (bump `schemaVersion`), or "last 24 h" proves the wrong window.
- **ADR-051 · Carryovers: `tomorrow.json` is untrusted input with a strict parser and a tolerant reader; shown only on its `forDate`.** The user's flow writes `tomorrow.json` (schema 1) into the exports folder at 4:30 pm. `CarryoverFileParser` is strict, in the style of `CalendarFileParser`. Duplicate keys are rejected. Unknown properties are **rejected** (not ignored) at the top level and per item, so a renamed field in the flow fails loudly. Comments and trailing commas are refused. `source` must be lowercase `todo`, `email`, `teams` or `other`. More than 10 items, or any string longer than 200 characters, is **rejected rather than truncated**. A NUL, raw or escaped, is refused; other control characters become spaces. The 64 KB limit is checked before reading. `CarryoverService` is tolerant: a missing file is "none", a half-written file or online-only placeholder is Unavailable, a bad file is a readable message, and it never throws to the UI. Real links (symlinks, junctions) are refused, but the plain reparse attribute is not, because OneDrive Files On-Demand sets it on every file. Items show only when `forDate` equals the local date (the clock's `LocalTimeZone`); otherwise the panel shows a gentle note. Nothing in the file is ever opened or followed, and items are never written to history. The Today panel reads it on load and on Refresh, under "Carryovers from yesterday" (heading, list semantics, ADR-047 live region, scalable fonts, system colours). · The flow is outside the app's trust boundary, and the panel must never crash or act on what it shows. · The flow needs more than 10 items or richer fields (schema 2).
- **ADR-052 · Alert outbox: one JSON file per alert in `outbox\`, deduped in memory, pruned conservatively, not subject to quiet mode.** `AlertOutbox` writes `outbox\<yyyyMMdd-HHmmss UTC>-<eventId "N">.json` (schema 1: `event`, `eventId`, `at`, `profile`, `workflow`, `workflowName`, `runId`, `step`, `message`; message scrubbed as in ADR-050). It fires when a run ends Failed (`run.failed`), lands in Needs attention (`run.needsAttention`, fed from the startup recovery decisions because that state never passes through the engine), or overruns (`run.overrun`). The engine has no run-level timeout, so overrun means a step is still running 5 min past its own timeout (or its action's default), which means it ignored cancellation. Overruns are checked every 30 s, once per run. The temp file is written beside `outbox\`, not inside it, then moved in, so the flow's "When a file is created" trigger never sees a partial file. Dedupe: at most one alert per workflow+event per 30 min, plus once per run. The state is **in memory**, so a restart can repeat an alert; the flow dedupes on `eventId`. A run suppressed by the window is not retried. A skipped write (folder missing) or a failed one is queued in memory and retried every 30 s for up to 30 min *(revised by ADR-054; the engine reports a run's end only once, so "the next time the run is seen" never came)*. Pruning keeps at most 200 files and none older than 7 days (by the name's timestamp). It only touches files directly in `outbox\` whose names match `^\d{8}-\d{6}-[0-9a-f]{32}\.json$`, never recurses, and never follows or deletes a link (a linked `outbox\` is not pruned at all). Honors `exports.alerts` and the fail-closed policy. **Quiet mode does not suppress the outbox**: quiet mode governs tray balloons (ADR-037), and the flow applies quiet hours itself. · The phone needs to hear about failures while the user is away, without the app making network calls. · Alerts must survive restarts exactly once (then persist the dedupe state in SQLite).
- **ADR-053 · The blueprint's HTTP `webhook.post` is replaced by the OneDrive outbox.** The phase 8-9 blueprint asked for an HTTP `webhook.post` action for alerts (in the spirit of the generic HTTP adapter in docs/ARCHITECTURE.md §10). Build rules 3–4 forbid network calls and listeners, and ADR-048's `NoNetworkSurfaceTests` (unchanged) enforce that. So the app writes files and the user's own Power Automate flow, already signed in to the Work tenant, does the posting. No HTTP client, socket, pipe, listener or telemetry was added. An HTTP action would need the user to **lift rules 3–4 explicitly**; it would then live in its own assembly with its own policy, per ADR-048, and would never be the default. · The rules are the user's, not the app's to relax. · The user lifts rules 3–4 for a named destination.
- **ADR-054 · Exports review fixes: nothing a run reports is lost, nothing runs after the final write, paths with spaces never leak.** *Status:* a `RequestSoon` that arrives while `status.json` is being built is counted, so the write that was already running no longer swallows it; a second write follows after the 30 s debounce. A failed write (OneDrive or antivirus holding the file) is tried again after 30 s instead of 15 min, and `AtomicFile` retries the move itself twice (100 ms, 300 ms) on a sharing or access error (not when a no-overwrite target exists). `needsAttention` is queried per profile (`IHistoryStore.GetExecutionsByStatus` gained a profile filter), so one profile's backlog can't hide the other's. *Alerts:* the engine reports a run's end once, so a run.failed / run.needsAttention alert whose write is skipped or fails goes into a small in-memory queue (at most 50) that `ExportsHub.Tick` drains every 30 s until it is written, switched off, refused, or 30 min old; it keeps its original `at`. Overruns need no queue because they are re-checked every 30 s. *Settings and log:* `StatusExporter.Changed` fires on every new state, so "last written" moves on while Settings is open. `exports.log` still gets one line per transition (outcome, folder state, or a new failure message), never one per routine write. *Shutdown:* `CoreHost.Dispose` calls `ExportsHub.Stop()` first, which cancels the loop and waits up to 2 s for a pass in flight, then makes the final write, then disposes the engine and history. *Start-up:* `ExportsHub.Housekeep` deletes leftover `.<name>.<32 hex>.ogoc-tmp` files at least 10 min old directly in each exports folder (no recursion, no links), as well as pruning the outbox. *Scrubbing:* `ExportText.Scrub` removes known roots (user profile, OneDrive roots, data root, temp and app-data) literally, then a quoted path up to its closing quote, then an unquoted path up to a quote, `< > |`, a line break, or punctuation followed by a space or the end, then any word that still holds a backslash. Folder and file names may contain spaces (`OneDrive - Org\HR\Salary review.xlsx`), so the old rule (a segment after a space only if it held a slash) leaked file names. Losing a few words after a path is the safe direction. *Simplicity:* one folder normaliser (`OneDriveBoundary.TryNormalise`/`IsSamePath`) serves the catalog and the use-time guard; one strict timestamp and date rule (`StrictJsonValues`) serves the calendar and carryover parsers; unused members (`GetStatusExporter`, `GetOutbox`, `ReadCarryovers`, `AlertWritten`, `HasItems`, `HasDetail`) are gone. *Accessibility:* every `OgocHeading` is a Level 2 heading; the carryovers heading stays at Level 3. · Code review of phases 8–9; ADR-050/052's own promises ("soon after any run ends", "retried"), and ADR-012 (nothing of the user's files leaves the PC in a status or alert). · The queue must survive a restart (persist it in SQLite), or scrubbing removes too much text to be useful (then quote paths in the messages the app writes itself).
