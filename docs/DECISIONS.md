# Decisions — OG Opossum Command Central

This is the log of every call I made or signed off on for this app, why I made it, and what would make me change my mind. The build ran through `build.sh`, with Claude Code doing the typing and writing these ADRs down as it went. I set the rules up front and pre-approved (22 Oct 2026) any choice that followed the spec, so nothing here happened behind my back. Every entry has the same three parts: decision · why · revisit when. The "revisit when" part is the honest one: it says what would prove the call wrong. Where it says "Never", I mean it, and future me is welcome to be embarrassed.

- **ADR-000 · Name.** Product "OG Opossum Command Central"; code name `OG_opossum_command` (exe `OG_opossum_command.exe`, data `%LOCALAPPDATA%\OG_opossum_command`). Supersedes "OPOSSUM CONTROL" in the spec. · My call. · Never.
- **ADR-004 · One tray process.** Hiding the window keeps workflows running; quitting stops them. · Simplest lifecycle for daily use. · Workflows must survive a full app exit.
- **ADR-005 · WPF on .NET 10 LTS.** · No MSIX packaging, mature tray support, per-user deployment. · A WPF limitation blocks a needed feature.
- **ADR-008 · SQLite for runs and history; JSON files for workflow definitions.** · Workflows stay hand-editable and diffable without an editor. · A visual editor is built.
- **ADR-011 · Calendar via Power Automate → OneDrive JSON file.** · Works with New Outlook; no app registration or admin consent. · IT approves a Graph app registration.
- **ADR-012 · Strict work/personal separation.** No data, tokens, or files cross the work and personal tenants; enforced in the engine, not just the UI. · Never.
- **ADR-013 · AI deferred.** Not part of this build. · Spec Phase 5 is started deliberately.
- **ADR-014 · Feasibility spike shape.** One console-type (`OutputType=Exe`) WPF project under `spikes/feasibility/Spike`, WPF `Application` and `TaskbarIcon` created in code (no App.xaml), SQLite opened with `Pooling=False` so the file can be deleted, 55 s watchdog in both modes. · `--check` must print to the console under `dotnet run` and exit on its own within 60 s; a second entry point from App.xaml would break the single-project rule. · The spike is deleted or the real Desktop project supersedes it.
- **ADR-015 · Repo-level `nuget.config` with nuget.org as the only source.** · The user-level `%APPDATA%\NuGet\nuget.config` on this PC has an empty `<packageSources>` list, so every single restore failed with NU1100, which is a hell of a way to say "you have no package sources"; the fix lives in the repo because the build never writes outside the project root (rule 5), and it makes restores reproducible on any machine. nuget.org is reachable anonymously; no sign-in is involved. · I add nuget.org to my user-level config, or the project moves to a private feed.
- **ADR-016 · Desktop entry point.** `OutputType=WinExe` (no console window for a tray app) with a hand-written `Program.Main` selected by `<StartupObject>`; `App.xaml` stays the `ApplicationDefinition` (no `StartupUri`) so later `--smoke-ui` runs with real resources. `--smoke-test` is handled before `App` is constructed; it writes to stdout, which a windowed exe only delivers when the caller redirects it, so the **exit code is the contract** and the build script checks only that. · Diagnostic modes must never show a window or run startup work; the gate captures output anyway. · A mode needs interactive console output (then split a console launcher).
- **ADR-017 · Tests on xUnit 2.9.3 + xunit.runner.visualstudio 3.1.4 + Microsoft.NET.Test.Sdk 17.14.1, versions pinned.** `Microsoft.NET.Test.Sdk` is the VSTest host the gate's `dotnet test --blame-hang-timeout` needs; it counts as "the xUnit runner" under rule 8. The template's `coverlet.collector` was removed (not on the allowed list, not needed). · The gate's exact command must work. · The gate moves to Microsoft.Testing.Platform.
- **ADR-018 · CA1707 and the underscore code name.** `AnalysisLevel=latest-recommended` flags `OG_opossum_command` as an assembly name and as a namespace. A namespace-scoped `SuppressMessage` does not match (Roslyn attributes the diagnostic to the innermost declared namespace) and an unscoped one disables the rule everywhere (verified with a probe). Yes, this is a lot of machinery for one underscore. I'm keeping the name. Instead, `CodeNameSuppression.cs` at the repo root is the first compile item of every project (via `Directory.Build.props`), carries the only `#pragma warning disable CA1707`, and declares an empty `namespace OG_opossum_command` so both diagnostics land inside the pragma. Every other identifier is still checked; a planted `Bad_Name()` method fails the build. · Rule 0 asks for the narrowest suppression. If compile order ever changes, the diagnostics reappear and the build fails loudly rather than widening. · Roslyn offers a precise way to suppress assembly-level diagnostics.
- **ADR-019 · CA1707 off under `tests/` only.** `tests/.editorconfig` sets `dotnet_diagnostic.CA1707.severity = none`, because test method names use underscores for readability. `src/` is unaffected. · Standard xUnit naming. · Never.
- **ADR-020 · AppPaths contract.** One sealed `AppPaths : IAppPaths` in Core resolves everything from one root: `OGOC_DATA_DIR` if set and **absolute**, else `%LOCALAPPDATA%\OG_opossum_command`. Blank values count as unset; relative values throw (never the current directory). Resolving is pure (creates nothing); `Resolve(getEnv, localAppData)` takes injected inputs so tests never mutate the process environment, and `FromEnvironment()` is the only production entry. Child paths (revised in Phase 3): `data.db`, `profiles\`, `profiles\<Work|Personal>\workflows\`, `logs\`; there is no shared `workflows\` folder because every workflow belongs to exactly one profile (ADR-012). · Rule 6, plus flaky parallel tests if they set env vars. · A path is needed outside the data root (it must be a new property here, not computed elsewhere).
- **ADR-021 · Root `Directory.Build.props` also governs `spikes/`.** The spike is not in the solution and is throwaway (ADR-014); it inherits the stricter analyzers but is never built by the gate. · One props file, no exceptions to maintain. · The spike is deleted.

## Phase 3 (core loop)

- **ADR-022 · Workflow schema v1 is strict and small.** Unknown properties, wrong types, non-slug ids, unknown actions, bad `dependsOn` (unknown, self, cycle), and `requiresApproval: true` are all errors; comments and trailing commas are tolerated; `trigger.type` is `manual` only; `onDuplicate` is `focus-existing` only; `onFailure` is `stop` | `continue`; there is **no `retry`**. Full contract in `docs/WORKFLOW-SCHEMA.md`. · Hand-edited files fail loudly on typos instead of silently doing something else; the reserved flag cannot be abused before the approval flow exists (ADR-013); retry of a process launch is unsafe (spec §06) and the other v1 actions finish instantly. · Schedules (Phase 2 of the spec), retry, or AI approval are built — each needs a schema bump, and old files must still load.
- **ADR-023 · Actions validate their own typed inputs at load time.** `IWorkflowAction.ParseInputs(JsonObjectReader)` turns the step's `inputs` object into a typed record (`UrlOpenInputs`, `FolderOpenInputs`, `ProcessLaunchInputs`) or records readable errors; the engine never sees a dictionary. `windows.process.launch` takes a full `.exe` path plus an argument **array** (passed to `ProcessStartInfo.ArgumentList`, no shell); `windows.url.open` accepts absolute http/https only, checked again at run time; `%VAR%` expansion happens at run time so files are portable. · Spec §07 (“avoid implicit string interpolation into shell commands”, “strongly validated DTOs at security boundaries”). · A scripting action is wanted (it gets its own action id and its own validation, not a relaxation here).
- **ADR-024 · In-process engine, one cancellation source per run, explicit process-tree kill.** `WorkflowEngine` runs on the thread pool with a `SemaphoreSlim` of `MaxConcurrentWorkflows` (default 2) run slots and `maxParallelSteps` step slots per run; each step gets a linked token with its timeout; on cancellation or timeout the process action calls `KillTree()` itself because a cancelled token is not process termination (spec §06). Every transition is saved before `ExecutionChanged` fires with an immutable snapshot (on worker threads; the UI marshals). `Interrupted` is only ever set by startup reconciliation; `NeedsAttention` exists in the enum but nothing sets it yet. · Simplest design that satisfies §06 and rule 8; snapshots make the UI and tests trivially thread-safe. · Resume/recovery review (spec Phase 2) is built, or a second host process is ever introduced (ADR-004).
- **ADR-025 · Profiles are fixed (Work, Personal); allowlist from an optional `profile.json`; default is every built-in action.** `profiles\<P>\profile.json` with `{"allowedActions":[...]}` narrows a profile; without it, the profile may run all registered actions. A broken policy file is reported in `ProfileCatalog.Errors` and on the smoke output, and the profile falls back to the default. The loader rejects disallowed actions per file and the engine refuses them again at `Start` (defence in depth, ADR-012). · In v1 every action is local and benign, so a typo in a policy file should not lock me out of my own tiles; the double check means a definition can never bypass the allowlist. · **Revisit (fail closed) the moment a network, M365, export, or AI action exists** — then an unreadable policy must deny those actions, not allow them. **Revised in Phase 5 by ADR-040** (the first M365 action exists: defaults and the broken-file fallback now exclude `m365.*`).
- **ADR-026 · Smoke modes never touch the real data root and run before the single-instance check.** `--smoke-test` and `--smoke-ui` use `OGOC_DATA_DIR` when set (the build script's scratch folder) and otherwise a fresh `%TEMP%\OG_opossum_command-smoke-<guid>` folder deleted on exit; both carry a 25 s watchdog that exits 1; both use `RecordingLaunchers`, so no browser, folder, or program opens (rule 7). `--smoke-ui` constructs the real `App` with `App.xaml` resources, shows `MainWindow` at (-32000,-32000) with `ShowActivated=false`, waits for `Loaded` and the dashboard's first bind, creates and disposes the tray icon, then shuts down. · Rules 5–7 and my smoke contract. · A smoke mode needs more than one profile's data (then give it its own fixture folder).
- **ADR-027 · Tray icon uses `System.Drawing.SystemIcons.Application`.** It comes from the WindowsDesktop shared framework that WPF already references, so no new package (rule 8); the spike proved the exact calls (`ToolTipText`, `Icon`, `ForceCreate`, `Dispose`). The context menu (Open / Switch profile / Quit) is built in code so the smoke runner can create and dispose it deterministically. · No icon asset exists yet and the generic icon is unmistakable in the tray. · An `.ico` is designed (then set `IconSource` from an embedded resource and delete this line).
- **ADR-028 · Single instance via session-local kernel objects.** `Program.Main` (after the smoke switches) takes `Local\OG_opossum_command.instance` as a named mutex; a second instance signals the auto-reset event `Local\OG_opossum_command.show-dashboard` and exits 0, and the first instance's background listener thread shows the dashboard. Both objects are session-scoped (`Local\`), need no elevation, and touch neither the registry nor the network (rules 2–4). · Spec §05 B (“one authoritative instance per Windows user”); pressing the shortcut twice should bring the window forward, not open a second app. · IPC beyond “show yourself” is needed (then a named pipe with an allowlisted command set, still local).
- **ADR-029 · Dashboard shows exactly six tiles; History is a separate view; closing hides to tray.** The first six workflows of the active profile (sorted by file name) fill the tiles and the rest are disabled “Empty slot” placeholders, so positions never shift (spec §14); files that fail validation are listed on the dashboard with their errors; the Active execution panel shows live steps and a prominent Cancel; Recent runs shows the last 8; the History view lists the last 100 runs with per-step detail and the redacted event log. Colours come from `SystemColors` dynamic resources so Windows high-contrast themes apply; every control has an automation name and the shared focus visual. The active profile is remembered in the `settings` table. · Spec §14 mock-up and the acceptance test “Accessibility”. · Favourites/ordering beyond file name, or more than six workflows per profile become common.
- **ADR-030 · Tests may start `cmd.exe` and `ping` as throwaway processes; such tests run in one xUnit collection.** `WorkflowEngineTests` and `WindowsProcessLauncherTests` share the `"real processes"` collection so their ping-process bookkeeping (snapshot PIDs, wait for the new one, assert it is gone after `KillTree`) is never interleaved; everything else uses `RecordingLaunchers`/`FakeProcess`. · Rule 7 permits exactly these throwaways; the first parallel run was flaky because two classes counted the same `PING.EXE` instances. · A dedicated test helper exe replaces `ping` as the long-running child.

## Phase 4 (reliability)

- **ADR-031 · `windows.script.run` runs trusted scripts only, from the profile's own `scripts` folder.** Inputs are an explicit `interpreter` (`powershell` → `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -File <script>`, or `cmd` → `cmd.exe /d /c <script>`), a bare `script` file name (no separators, no `..`, extension must match the interpreter, resolved path re-checked at run time to be inside `profiles\<P>\scripts`), and an `arguments` array. It reuses `IProcessLauncher` (8 KB per-stream capture, redaction, process-tree kill), so tests and smoke modes stay fake. A PowerShell refusal is detected from the output ("running scripts is disabled", `PSSecurityException`, `UnauthorizedAccess`, …) and reported as `execution-policy-blocked` with the options spelled out; the app **never** passes `-ExecutionPolicy` (rule 2). Tests run a real `.cmd` only; PowerShell behaviour is tested with fakes because policy on this PC may block `.ps1` and the app must not try. · Spec §07/§09 ("treat shell and PowerShell as explicit trusted-action categories"). · A third interpreter is wanted (add a fixed path here; never a free-form path).
- **ADR-032 · Workflow schema v2 is additive; v1 files keep loading.** `CurrentSchemaVersion` is 2, `OldestSupportedSchemaVersion` is 1. New in v2: `trigger.type: "schedule"`, per-step `locks`, top-level `aliases`. A file that says `schemaVersion: 1` and uses any of them is rejected with "needs schemaVersion 2", so an old file never silently gains behaviour. `docs/WORKFLOW-SCHEMA.md` is the contract. · ADR-022 asked for a bump with backwards compatibility. · v3.
- **ADR-033 · Resource locks are engine-wide, taken in sorted order, released in `finally`.** A step may declare `locks: ["window:<name>", "file:<full path>", "custom:<name>"]`; keys are normalised at load time (`file:` → absolute, upper-cased, `%VAR%` expanded; others verbatim with a lower-case kind). `ResourceLocks` holds one `SemaphoreSlim(1,1)` per key for the whole engine, so the same key serialises steps across different runs and workflows even with `maxParallelSteps > 1`. The wait observes the step's own token, so Cancel while waiting takes nothing; a step waiting for a lock stays `Running` with "Waiting for …" and occupies one of the run's parallel slots (accepted; the alternative would reorder steps). · Spec §06 concurrency policy. · Lock contention becomes visible in daily use (then add a dedicated Waiting state).
- **ADR-034 · Scheduler: definition in the file, state in SQLite, `last_fired_for` written before any run starts.** `trigger.type: "schedule"` needs `at` (HH:mm list), an explicit `timeZone` (Windows or IANA ID, validated at load), optional `days`, `missedRuns` (`skip` default | `run-once` | `catch-up-limited` + `catchUpLimit` 1–10), and `expiresAfterMinutes` (default 5). `OccurrenceCalculator` is pure: a time inside a spring-forward gap runs at the first minute that exists; a time inside a fall-back fold runs once, at its first (daylight) pass; the machine's zone is never consulted. `Scheduler.Tick(now)` computes occurrences since `last_fired_for` (capped at 7 days back), splits them into on-time (within the expiry window) and missed (policy), persists `last_fired_for = latest` **before** starting anything (a crash loses at most one run, never repeats one), then dispatches per trigger: on-time occurrences start immediately and are **suppressed** if the workflow is still active (focus-existing); catch-up runs are awaited one after another so the limit means what it says. `Reconcile` registers new or changed schedules from *now* (nothing before they existed counts as missed), keeps state for unchanged ones, and deletes rows whose workflow is gone. A background loop ticks at the next due time, at most every 30 s, using `TimeProvider` so tests inject a clock and call `Tick` directly. While paused (`scheduler.paused` setting) due occurrences are recorded as skipped, so unpausing never fires stale runs. Scheduler decisions without a run (skipped, suppressed, paused) surface as `SchedulerEvent`s and in `triggers.last_outcome`, not as execution events (those need an execution id). · Spec §08 and the acceptance test "Scheduler". · Event or calendar triggers (new `type`, same table).
- **ADR-035 · Crash recovery: classify, auto-resume only what is provably safe, otherwise Needs attention with Resume / Dismiss.** *(Revised by ADR-046: runs found Cancelling end Cancelled; failed or cancelled non-idempotent steps also block auto-resume.)* `MarkInterrupted` now returns the IDs it touched and sets `recovery = pending`; after workflows load, `RecoveryReviewer` classifies each: workflow file missing → Needs attention; `executions.workflow_hash` (new) differs from the current file → Needs attention; any step that was *running* at the crash whose action is `NonIdempotent` → Needs attention naming the step; otherwise a new run starts automatically (`trigger_source = recovery`, `resumed_from` = old id) with the already-Completed steps marked Completed and not repeated. The original run ends `Interrupted` with `recovery` = `auto-resumed` | `resumed` | `dismissed`, or `NeedsAttention` with the explanation in `error`. Resume uses the *current* file. The engine tolerates the journal closing underneath it (a crash or shutdown) without unobserved exceptions. · Spec §13 recovery algorithm; §17 Phase 2 exit criterion "no silent duplicate side effects", proven by tests that close the journal under a running engine. · Adapters gain reconciliation (e.g. "is that process still running?"), which could turn some Needs attention cases into safe resumes.
- **ADR-036 · Single-instance lock lives in Core; smoke modes are exempt; Core declares `SupportedOSPlatform("windows")`.** `SingleInstanceLock.Acquire(name)` tests ownership with `WaitOne(0)` on `Local\<name>.instance` (not `createdNew`, which a lingering handle can fool), owns the `Local\<name>.show-dashboard` auto-reset event, and raises `ShowRequested` on a listener thread; `SignalExisting` is what the second launch calls. Names are parameterised so tests use unique ones; a Windows mutex is re-entrant per thread, so the in-process "second instance" tests acquire on another thread. `Program.Main` runs the smoke switches *before* taking the lock, and a test proves it: it holds the production lock and starts the real exe with `--smoke-test` (path baked into the test assembly as `AssemblyMetadata` by the csproj, built first via a `ReferenceOutputAssembly=false` project reference) with `OGOC_DATA_DIR` set to a throwaway folder in the child's environment. Named kernel objects are Windows-only (CA1416), so Core and the tests carry an assembly-level `SupportedOSPlatform("windows")` rather than changing the TFM. · Spec §05 B; the brief's test requirement; rule 11 with `-warnaserror`. · Core must ever run off Windows (it will not).
- **ADR-037 · Notifications go through one injectable sink; quiet mode suppresses everything below Error.** `NotificationService` (Core) turns engine results and scheduler decisions into `Notification(Level, Title, Message)`; Completed = Info, Cancelled/skipped/suppressed = Warning, Failed/Needs attention/refused = Error. With `ui.quietMode = true` only Error gets through (a failed run or one that needs me is never silent). The Desktop sink shows tray balloons via `TaskbarIcon.ShowNotification` on the dispatcher; `--smoke-ui` and tests use `RecordingNotificationSink`, so the build never pops a balloon (rule 7). · Spec §14 "quiet mode and notification severity thresholds". · Windows toast notifications (would need an AppUserModelID; a per-user shortcut is acceptable under rule 2, but not needed yet).
- **ADR-038 · Global hotkey via `RegisterHotKey` on the hidden main window; failure is reported, never thrown; the palette is a separate topmost window.** Default `Ctrl+Alt+Space`, stored as text in `ui.hotkey`, parsed by `HotkeyGesture` (at least one modifier plus one key). `GlobalHotkey` registers on the main window's HWND (`EnsureHandle`, so it works while hidden) and reports `ERROR_HOTKEY_ALREADY_REGISTERED` as "in use by another app; change it in Settings" in the host status line. Not registered in `--smoke-ui` (a build must not grab a system-wide key). P/Invoke uses `DllImport` with `DefaultDllImportSearchPaths(System32)` because `LibraryImport` would need `AllowUnsafeBlocks` project-wide. The palette searches both profiles (`CoreHost.Search`: alias/name equal > starts-with > id starts-with > contains) and labels each row with its profile; Enter runs under that profile, so ADR-012 is unaffected. `--smoke-ui` constructs the Settings view and the palette off-screen so XAML errors fail the gate. · Spec §08 trigger family 1 and §14 "global command palette with human-readable aliases". · A low-level keyboard hook is needed (it is not: hotkeys are enough and far less invasive).

## Phase 5 (calendar without app registration)

- **ADR-039 · Calendar = one read-only local JSON file per profile, written by my own flow; strict schema, tolerant reader.** `m365.calendar.readFile` reads the profile's `CalendarFilePath` (from `profile.json` `calendarFile`, else `AppPaths.GetDefaultCalendarFile`: Work → `%OneDriveCommercial%\OG_opossum_command\calendar.json`, Personal → none). The path never comes from a workflow file. `CalendarFileParser` is strict (exact keys, `schemaVersion` 1, ISO 8601 timestamps **with an offset**, bare dates only for all-day events, https-only links, at most 500 events) because the Outlook connector exposes offset-less start/end fields that would silently shift every event. `CalendarService` is tolerant: missing, empty, locked, or not-JSON-yet (mid-sync) files are retried once after 750 ms and then reported as `Unavailable`, and the step **completes**. Only well-formed JSON in the wrong shape (`calendar-invalid`) or a cross-context path (`calendar-refused`, ADR-040) fails the step. It never throws for a bad file. Staleness is judged from `generatedAt` (default 60 min, step input `maxAgeMinutes`), never from the file's mtime. Online-only OneDrive placeholders (offline/recall attributes) are not opened, because opening one triggers a download. The calendar reader never creates or writes anything under OneDrive *(revised in Phase 8 by ADR-050: the exports write `status.json` and `outbox\*.json` into the same app folder)*. Event content stays in memory (`GetLatest`); history stores the status line and counts only. `dashboard.schedule.show` goes through a new `IDashboardPresenter` on `LauncherSet` (the App on the dispatcher; a recorder in tests and smoke runs) and never reads the file itself. It switches the window to the run's profile (and remembers that choice), so a scheduled Work run ending in this step brings up Work even if Personal was showing, which is deliberate: it shows *that run's* schedule. The Today panel reads on profile load and on **Refresh**, with no timer. `AppPaths` gained the OneDrive roots from the same injected environment lookup; `ForRoot` resolves none, and the smoke modes now use `ForRoot(OGOC_DATA_DIR)` instead of `FromEnvironment`, so a build-time smoke run never looks inside my real OneDrive (rule 5). The flow itself is my job (`docs/POWER_AUTOMATE_FLOW.md`, standard connectors only). · ADR-011 (no app registration; New Outlook has no COM), rules 3–5, and the brief's "never crash". · IT approves a Graph app registration (then a Graph reader replaces the file behind the same `CalendarService`), or the flow needs fields beyond the seven in schema 1 (bump `schemaVersion`; keep reading 1).
- **ADR-040 · `m365.*` actions are Work-only by default and fail closed; a path guard backs up the allowlist.** With no `profile.json`, Work may run every built-in action and Personal every action except the `m365.*` family. A broken policy file now falls back to *every built-in action minus `m365.*`* for either profile, revising ADR-025: local tiles keep working and M365 data is denied. Even when a Personal policy explicitly allows `m365.calendar.readFile`, `CalendarService` refuses any path inside `%OneDriveCommercial%`, and Work any path inside `%OneDriveConsumer%` (after `GetFullPath`, so `..` doesn't help). That makes three independent layers: the loader rejects the file, the engine refuses at `Start`, and the service refuses the path. The guard lives in the service, not only the action, because the dashboard reads through it too. · ADR-012 ("enforced in the engine, not just the UI") and ADR-025's own revisit trigger. · A personal calendar feed is wanted (then a Personal `calendarFile` outside the work OneDrive plus an explicit allowlist entry; the guard already permits that).

## Phase 6 (hardening)

- **ADR-041 · Four adversarial reviews, each verified, fixes on separate worktrees.** Reviewers covered security, stress correctness, accessibility, and simplicity. Each finding then went to a second agent told to refute it. Only the confirmed findings were fixed: 7 of 8 security, 16 of 20 correctness, all 12 accessibility, 12 of 15 simplicity. The refuted ones are C16, C17, C19, C20 (timeout labelling, dispatcher ordering, expiry of resumed scheduled runs, clock-jump spin), SEC-5 (OneDrive alias spellings; the guard is for accidents, not for stopping the person at the keyboard), and S11, S14, S15 (`IHistoryStore` seam, the spike, reserved schema fields). · Unverified findings would add risk without fixing anything. · Before the first organisational release, repeat the review.
- **ADR-042 · `cmd` scripts get no shell metacharacters; cmd starts in the scripts folder.** For `interpreter: "cmd"` the loader refuses any argument containing `& | < > ^ % ! " ( )` or a line break, and refuses script names with spaces. It checks the arguments again after `%VAR%` expansion, refuses a UNC scripts folder, and starts `cmd.exe /d /c .\<script>` with the scripts folder as working directory, so the folder path never appears on the line cmd re-parses. That line also never starts with a quote, so cmd's quote stripping can't mangle it. The launcher still takes only an argument array (ADR-023). · cmd re-parses everything after `/c`, so an argument array is only an array when no element is special to cmd. Raw command-line support was rejected so that "no shell strings" stays true. · Someone needs `%VAR%` or metacharacter arguments for cmd (the answer today: use the `powershell` interpreter).
- **ADR-043 · `windows.process.launch` refuses shells and script hosts.** The refused programs are `cmd`, `powershell`, `powershell_ise`, `pwsh`, `wscript`, `cscript`, `mshta`, `rundll32`, `regsvr32`, `wsl`, `bash`, `conhost` and `forfiles`. They are matched by file name, ignoring case, after `GetFullPath`, at load and again at run time (`interpreter-refused`). "Allowed executable" (spec §18 Launch) therefore means a full `.exe` path that is not one of these, inside a profile whose allowlist permits the action. · Otherwise `powershell -ExecutionPolicy Bypass -Command …` or `cmd /c …` skips every ADR-031 rule and any allowlist that leaves out `windows.script.run`. · A legitimate tool ships under one of these names, or name matching proves too weak (8.3 names, renamed copies; the author is the local user).
- **ADR-044 · Strict input: duplicate JSON keys are errors; NUL is checked before `%VAR%` expansion.** `AllowDuplicateProperties = false` applies to workflow files, `profile.json`, and the calendar file. A NUL in a path, a lock, or `calendarFile` is a readable load error, and the calendar service returns Unavailable for it. · `JsonDocument` lets the last duplicate win silently, and `ExpandEnvironmentVariables` cuts a string at a NUL, so a folder path could quietly open its parent. · A tool we read legitimately writes duplicate keys.
- **ADR-045 · Redaction is central, broader, and bounded twice.** `SqliteHistoryStore` scrubs every run error, step message, step output, and recovery explanation it stores. The engine also scrubs step messages and run errors before publishing them (500 characters), so the dashboard and tray never show raw text. The store's own cap sits above the engine's, so nothing is cut twice. New patterns: underscore-prefixed keys (`DB_PASSWORD=`, `GITHUB_TOKEN=`), `Authorization: Basic|Digest|NTLM|Negotiate`, quoted values with spaces, `--token value` style flags, URL user info, and prefixed tokens (`AKIA…`, `ghp_…`, `github_pat_…`, `glpat-…`, `xox?-…`, `sk-…`). The calendar parser no longer echoes a rejected link. · Spec §13 and §18 Output require it, and any caller that forgets to scrub would otherwise leak. · A new secret shape turns up in real output (add a pattern and a test).
- **ADR-046 · Every run transition is saved before it is announced. Recovery reads its work from the database, and a cancel is final.** Each run has a save gate (snapshot and write together). The Queued, Running, Cancelling, step, and terminal states are all persisted before `ExecutionChanged`. A resumed run records its already-completed steps when it is queued. Recovery reviews every row with `recovery = 'pending'`, not just this boot's list, and each run is reviewed in its own try/catch. Auto-resume is blocked by any non-idempotent step that started, whether it ended Interrupted, Failed, or Cancelled. A run found **Cancelling** at startup ends **Cancelled** and is never resumed. This revises ADR-035, where Cancelling became Interrupted. The engine refuses `Start` once shutdown begins, and Quit stops the scheduler first. After a process exits, the output drain waits at most 2 s, so a grandchild that holds an inherited pipe can't hang a step. The scheduler loop survives store errors and throwing subscribers (it backs off 30 s and records `scheduler.lastError`). · Spec §17: "no silent duplicate side effects during simulated interruption". If I hit Cancel, I meant it. · Saves become a bottleneck (switch to a version column), or detached grandchildren need Job-object containment.

- **ADR-052 · Alert outbox: one JSON file per alert in `outbox\`, deduped in memory, pruned conservatively, not subject to quiet mode.** `AlertOutbox` writes `outbox\<yyyyMMdd-HHmmss UTC>-<eventId "N">.json` (schema 1: `event`, `eventId`, `at`, `profile`, `workflow`, `workflowName`, `runId`, `step`, `message`; message scrubbed as in ADR-050). - **ADR-054 · Exports review fixes: nothing a run reports is lost, nothing runs after the final write, paths with spaces never leak.** *Status:* a `RequestSoon` that arrives while `status.json` is being built is counted, so the write that was already running no longer swallows it; a second write follows after the 30 s debounce. ## Opossum Maid (tidy-up)

- **ADR-058 · Opossum Maid: the engine lives in Core, the CLI is `tools/OpossumMaid`, and the desktop only plans.** Opossum Maid tidies the work download inbox (`%OneDriveCommercial%\_Inbox`) and `%USERPROFILE%\Downloads`. The CLI is a new console project, `tools/OpossumMaid` (`OpossumMaid.exe`, no underscore in the assembly name so it doesn't lean on ADR-018). - **ADR-059 · Content extraction is local. PdfPig is the fourth runtime dependency.** PDF uses **PdfPig 0.1.16** (Apache-2.0, pure managed, no dependencies on net8+, about 2 months old when pinned). It reads document info (title, author, keywords) and the words of the first 5 pages, and a new baseline counts as a new line. DOCX, XLSX and PPTX are ZIP packages of XML, so they go through `ZipArchive` and a DTD-free `XmlReader`: no Office, no interop. TXT, MD, CSV, JSON, code, RTF and HTML get the first 256 KB. HTML also gets its `<title>` and the "saved from url" marker. Screenshot versus camera is a heuristic (name, software, screen-sized PNG with no camera tags). Every extractor treats the file as hostile. Over 64 MB means no text read. Zip entries are capped at 4 MB, and there's a 10 s timeout per file, after which the parser is abandoned. A failure is a note in the report, never a crash. Text is capped at 8,000 characters. **Never opened at all**: credential-looking names (ADR-061), OneDrive online-only placeholders (opening one downloads it, same rule as ADR-039), and links (never followed). · I looked hard at writing my own PDF text-stream extractor to keep it at three dependencies. No OCR: a scanned PDF is classified from its name and metadata, and the report says so. · PdfPig gets a security advisory or goes unmaintained, or scanned PDFs turn out to be the majority (then Windows' own OCR via WinRT, Desktop only).
- **ADR-060 · Maid config is three strict JSON files, seeded once.** `rules.json` (sources, roots, thresholds, signals), `taxonomy.json` (categories), and `learned.json` are written with defaults the first time they're missing and never overwritten after that. A source marked one side that lives inside the other side's root is skipped. - **ADR-061 · The classifier is rules, not a model, and the work/personal wall comes first.** Order: learned rules, then content rules, then defaults. Each verdict carries plain-words reasons. *What it is*: format first (installer, archive, code, dataset, design asset, media, partial download, saved page, photo, screenshot), then phrase rules (invoice, receipt, statement, tax form, certificate, contract/lease, form, resume, medical, ticket, schedule, report, letter). *What it's about*: keywords by frequency, with title and name words counted three times, plus named things (capitalised phrases ending in an organisation word, phrases that recur, e-mail domains). *Side*: a file found in the work inbox is Work, and one found under the personal root is Personal. That's 0.9, and the location wins. If the content strongly says the other side (≥ 0.7 and clearly ahead), it's a **cross-side suspect**. It gets marked "needs your decision" and never moves by itself. Downloads belongs to neither side. A file there only gets a side from evidence (`workSignals` and `personalSignals` in `rules.json`, the Office Company property, learned rules, taxonomy fit), and it needs 0.7. Taxonomy fit alone tops out around 0.67 by construction, so "it sounds like a camp roster" can't put a file on the work side. Below 0.7 it's "needs your decision", with the likely side shown. *Credentials* (rule 5): names matching recovery codes, backup codes, password(s), passphrase, credentials, secrets, private key, `id_rsa`, API or access keys, tokens, 2FA/MFA, seed phrase, wallet, login, PIN, or extensions `.pem .pfx .p12 .key .kdbx .kdb .env .ppk .jks .gpg .asc .ovpn .rdp .cer .crt …` are SECURITY. They're never opened, not even to hash them, and never moved or bundled. Extracted text that looks secret-shaped (a private key block, `password: …`, known token prefixes) also makes a file SECURITY. *Taxonomy*: at most 8 categories per side, one level each, plus an optional category\subfolder, so never deeper than two. Work: Programs, Reports, Events, Admin, Brand, Archive, with `_Inbox` as the fallback (unsure work files stay put). Personal: Home, Money, Career, Health, Hobbies, Media, Dev, with `_Review` as the fallback. Detail goes in **tags** (doc type, entities, keywords, year for official documents, group label), not in more folders. Confidence is the lowest of side, category and doc-type confidence. Items at 0.75 and up come pre-ticked. · A folder tree I can hold in my head, and a wall that holds even when the content is ambiguous. ADR-012 says "Never", and I meant it. · Corrections show the defaults are wrong for most files after the first couple of weeks.
- **ADR-062 · Junk is a proposal, protected documents are never junk, and duplicates are per side.** Junk: exact duplicates by SHA-256 (keep the copy whose name has no copy marker, then the oldest), unfinished downloads (`.crdownload .download .part .partial .tmp`, review if under an hour old), installers (review if under 7 days old), empty files, a `X_files` folder whose page is gone, superseded versions (`v1`/`v2` when a `final` exists; without a final, older versions are only review), archives already extracted next to themselves, and screenshots over 90 days old that were never edited. Same text with different bytes is review, not junk. Duplicates count only within one side: a work copy and a personal copy of the same file are two files, not one junk. **Protected** means invoice, receipt, statement, tax form, certificate, contract, medical, form, digitally signed, or mentions a signature or a notarisation. Protected files are kept, and at worst marked review. Junk goes to `<source>\_Trash Review\<run>\<relative path>`, so it never crosses a side and undo is an exact reverse. The scanner never reads `_Trash Review`. · The maid exists to separate garbage from what I need, and the cost of a wrong "junk" on a lease is way higher than the cost of a stale installer. · Review piles up and nobody looks at it (then lower the bar for specific rules, one at a time).
- **ADR-063 · Short names: 40 characters, title case, noise out, no dates unless that's all there is.** `NameCleaner` strips copy markers (`(1)`, `copy`, `Copy of`), GUIDs, long hex hashes, camera prefixes, ISO, compact and written-out dates, times, `final`, `latest` and version markers. It turns `_`, `.` and dash separators into spaces, keeps a real hyphen (`E-ticket`), keeps a bare year (`Taxes 2024`), keeps acronyms and mixed-case brands, and cuts at a word boundary. A name that is only noise (`Scan_0001`, `document (3)`, `IMG_1234`) is rebuilt from the content: the entity plus the doc type (`Contoso Bank Statement`), else the metadata title, else the doc type plus a date. A saved web page and its `_files` folder are never renamed, because the page refers to the folder by name. · The file's own metadata already holds the dates. Long names don't help me, and they don't help Microsoft 365 search either. · Search proves that names with dates work better (then make it a setting).
- **ADR-064 · Files that belong together move together.** `Grouper` uses union-find over: the same first folder under a source (strongest), a saved page and its folder, versions of one base name, and the same named entity among files leaning the same way. Inside a group, the moving members on one side take the category with the highest total confidence. A group that already shared a folder, with three or more movers, keeps that folder name as the subfolder (`Programs\Summer Camp`). Every other group just adds its label as a tag. A saved page's `_files` folder always copies its page's action, side and destination. · I'd already grouped those files by hand once. Splitting them up again would be the opposite of tidying. · Groups get merged that shouldn't be (then drop the entity edge first, it's the weakest).
- **ADR-065 · The plan is a JSON file you can edit plus an HTML page you can read, and both stay on the PC.** `plans\<plan>.json` lists every item: action (`move`, `trash`, `leave`, `decide`, `security`), approved, origin, side, category, subfolder, name, doc type, tags, keywords, entities, confidence, reasons, group, verdict, protected, who decided (`rules`, `learned`, `ai`, `you`), size, mtime and hash when planned, plus the first proposal for learning. The plan has a top-level `approved: false` that only `approve` (or me editing the file) flips, and `apply` refuses without it. Plans and reports name real files, which is fine because the data folder never syncs anywhere. · I want to read the whole plan in a minute and fix it in another. · The plans get too big to read (then add a filter view).
- **ADR-066 · Apply re-checks everything, journals before it moves, never overwrites, and learns from what I changed.** At apply time each approved `move` or `trash` item is checked again. The source must be inside one of this PC's maid sources, its origin side must match where it lives, it must still exist, and it must be unchanged (size plus mtime within 2 s). The side root must exist (a OneDrive root is never created; the personal root may be, if its parent exists). The category must be in the taxonomy, the subfolder must be one safe name, and the destination must sit inside its side's root and outside the other's. And a move from one side to the other needs `crossSideConfirmed`, which only `learn --side` sets: hand-editing `side` isn't enough. `decide` and `security` items never run, even when ticked. Each move is written to `runs\<run>.jsonl` as `pending`, flushed, moved, then written `done`, so a crash in between can still be undone. Folders the run creates are journalled too. A taken name gets ` (2)`, ` (3)` and so on, and the report says so. Nothing is ever overwritten. Applying the same plan again skips what an earlier, not-undone run already placed. `undo <run>` reverses newest first, refuses to move back a file whose hash changed since (it was edited after the move), uses ` (2)` if the original name has been taken meanwhile, removes only the folders that run created and only once they're empty, and writes `runs\<run>.undo.jsonl`, so a second undo does nothing. *Learning*: `learn <plan> <item> --side/--category/--subfolder/--name/--tag/--keep/--junk` edits the item and records a rule in `learned.json`, keyed on the item's top entity, else its top keyword, else its base name ("files mentioning Contoso Bank are Personal / Money"). Repeating a correction raises its weight, and contradicting it starts the count again. `apply` also learns from category, side or action edits made by hand in the plan file. Learned rules come first in the next classification, which is how the first week of corrections teaches it. · The planner's checks mean nothing if a stale or edited plan can skip them. Nothing gets deleted, nothing gets clobbered, and I can always get back. · A run needs to touch thousands of files (then batch the journal flushes).
- **ADR-067 · Exactly one file in the maid may remove anything, and purge only recycles.** `Maid/MaidDeletion.cs` holds the only two removals: an empty folder that undo is cleaning up (never recursive), and `purge`. `ApplyUndoTests` text-scans every other `.cs` file under `Core/Maid` and `tools/OpossumMaid` for `File.Delete(`, `Directory.Delete(`, `.Delete(`, `SHFileOperation`, `DeleteFile(` and friends, and fails if it finds one. `purge` only considers files that a run put in `_Trash Review` and that were not undone. With `--confirm` it sends them to the **Recycle Bin** through `SHFileOperation` with undo allowed and no UI, never a permanent delete. Even the explicit purge leaves me one more way back. · Never.
- **ADR-068 · Tags go in a sidecar index (personal) and a CSV (work), not in the files.** Personal moves update `maid\exports\personal-tags.json` (path → tags, category, doc type, run), and undo removes those entries. - **ADR-069 · The AI step is a file hand-off to Claude Code, personal files only.
